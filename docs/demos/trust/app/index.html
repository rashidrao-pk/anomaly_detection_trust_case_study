Can I trust my anomaly detection system?

A VAE-GAN trained only on good hazelnuts and screws flags a part when its reconstruction differs too much from the input. This page replays that pipeline on the samples discussed in the paper, one stage at a time, and then asks the question the anomaly score cannot answer by itself: was the part flagged because of its defect?

1Detect: reconstruct and compare

The encoder maps the image ξ to a 32-dimensional code, and the decoder turns its mean back into ξ′, the closest thing to a good part the model knows. The anomaly map takes, per pixel, the largest colour difference, and the anomaly score is the single largest value of the map:

m = maxc |ξ′ − ξ|,  α = max(m)

Point at any panel to read the three images at the same pixel. The ring marks the one pixel that sets α.

3Explain: which regions make the error large?

The anomaly map mixes the defect with everything the decoder renders poorly. LIME and SHAP separate the two by asking the model directly. Both explain the same quantity, the reconstruction loss f(x) = Σ (d(e(x)) − x)², and both hide a region by pasting in the reconstruction there.

LIME cuts the image into k≈100 Quickshift superpixels, computed on (ξ+ξ′)/2 (setting S1). Each of n = 5000 perturbations keeps a random half of them, and a weighted ridge regression of f on the kept/hidden pattern gives one weight β per superpixel. Setting S2 cheats on purpose: its segmentation also sees γ, so the defect gets superpixels of its own, which isolates what the segmentation alone costs. SHAP (setting S3) uses the partition explainer on a recursive split of the pixel grid, with no superpixels at all.

4Verify: does the explanation land on the defect?

An explanation β is a real-valued map; the ground truth γ is a binary mask. Keeping the pixels with β ≥ θ gives a binary explanation γ′, and the Jaccard index J(γ,γ′) = |γ∧γ′| / |γ∨γ′| measures the overlap. Since no θ is right for every image, the paper reports, per sample, the best one: maxθ J. A low maximum means that no cut of the explanation matches the defect, so the part was flagged, or missed, for some other reason.

How it was computed

Everything above comes from the paper's own pipeline and its trained 30 000-epoch checkpoints, run unchanged: the notebook's binary search for 100 Quickshift superpixels, LimeImageExplainer(random_state=1234) with the reconstruction as hide colour, and the SHAP partition explainer with an Image masker on ξ′, each with a budget of 5000 model calls.

def f(batch):                                   # the paper's lime_predict_loss
    mu, _, _ = model.encoder(batch)
    return ((model.decoder(mu) - batch) ** 2).sum(axis=(1, 2, 3))[:, None]

segments = search_segment_number((xi + recon) / 2, 100)          # S1
lime = LimeImageExplainer(random_state=1234).explain_instance(
    xi, f, hide_color=recon, num_samples=5000, segmentation_fn=lambda _: segments)
shap_values = shap.Explainer(f, shap.maskers.Image(recon, recon.shape))(xi[None], max_evals=5000)

The compute script wraps LIME's data_labels to log every perturbation it draws and every loss the model returns, then refits LIME's own ridge regression on the first n rows of that log; it checks that the fit on all 5000 rows equals the explanation explain_instance returned. The page only looks values up. Step 2 uses the paper's full test sets: scores and Jaccard maxima from the archived result CSVs, and the score axis read back from the vector Fig. 2.

Run it again

The scripts are in docs/demos/trust/compute. config.toml lists the samples, the budgets and the MVTec AD path; change it to explain other images, and run:

python explain.py                      # a few minutes per sample on a laptop CPU
python pack.py                         # the page's data, ../assets/data.js
